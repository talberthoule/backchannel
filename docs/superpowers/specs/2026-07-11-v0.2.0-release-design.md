# Backchannel v0.2.0 Release - Design

Date: 2026-07-11
Status: Approved

## Goal

Publish every Backchannel change since `v0.1.1` as `v0.2.0` across the
repository's existing delivery paths: source-built Docker Compose images, the
Cloudflare documentation site, and portable Linux, macOS, and Windows desktop
bundles.

## Release Contents

The release includes the complete `v0.1.1..HEAD` history, especially:

- secure early-access interest capture and the private operator admin page;
- richer meeting chat grounded in briefings, saved insights, and transcripts;
- clearer interest-request failures and hardened chat context handling; and
- a Linux x64 desktop bundle alongside the existing Windows x64 and macOS
  arm64 bundles.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Version | `v0.2.0` | The release adds user-facing features and a new supported desktop platform |
| Integration | Fast-forward `master` to the clean release branch | The release branch already contains `master` and is pushed without divergence |
| Desktop publication | Push the annotated tag before `master` | Existing release policy requires verified assets before public download links change |
| Desktop access | Keep GitHub release assets private | No approval was given to change repository or installer visibility |
| Docker | Rebuild and validate current Compose definitions | Docker users build from source; no registry or new Compose behavior is needed |
| Version source | Tag plus release metadata | The repository has no runtime version file, so adding one would create redundant state |
| Change control | Release notes, release commit, tag, and GitHub Release | These are the repository's existing authoritative records; no parallel changelog is needed |

## Files and Publication Flow

Add `.github/release-notes/v0.2.0.md` and
`site/releases/v0.2.0/index.html`. Update current-version and platform links
in `README.md`, `docs/quickstart.md`, `site/index.html`, comparison pages,
`site/llms.txt`, and `site/sitemap.xml`. Historical release pages remain
unchanged.

Prepare the release on `master`, run the repository's backend, desktop,
frontend, docs-site, Compose, audit, and diff checks, then commit the release
metadata. Create an annotated `v0.2.0` tag on that commit and push the tag.
After the tag-triggered workflow passes and all three exact assets are
available with authenticated access, push `master` to publish the site and
Docker source. Verify the deployed release page and links.

## Desktop Contract

The release workflow must produce and smoke-test these exact assets:

- `Backchannel-windows-x64.zip`;
- `Backchannel-macos-arm64.zip`; and
- `Backchannel-linux-x64.tar.gz`.

Windows and macOS remain unsigned portable bundles, not MSI or DMG installers.
Linux remains a portable tarball, not a DEB, RPM, or package-manager release.
Installation documentation must state those limits and the existing first-run
steps.

## Failure Handling

Do not push `master` if any release check or desktop matrix job fails. Fix
source or metadata before tagging when possible. If a tagged bundle has a code
or packaging defect, publish a new patch version rather than moving or
force-pushing `v0.2.0`. Site-only corrections may follow as a normal `master`
commit under the existing recovery policy.

## Verification

The release is complete only when:

- backend and desktop unit suites pass;
- frontend and docs-site production builds pass;
- the production dependency audit passes;
- Compose configuration and backend/frontend image builds pass;
- `git diff --check` and the structural gate pass;
- the tag points to the release commit;
- all three desktop workflow jobs and authenticated asset checks pass;
- anonymous desktop asset access remains denied;
- the Cloudflare site deployment passes and the `v0.2.0` release page returns
  HTTP 200; and
- `master`, `origin/master`, and the release worktree are synchronized and
  clean.
